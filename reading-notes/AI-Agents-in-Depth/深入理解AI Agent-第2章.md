# 《深入理解 AI Agent：设计原理与工程实践》

## 第二章：上下文工程——模型每次决策的“工作台”

**在总链路中的位置：**本章聚焦“信息已经准备好之后，怎样组织成模型本轮真正看得到的上下文”。它主要讲运行时的工作台，不等同于上游的记忆库或文档库。

### 2.1 为什么上下文是核心，而不只是提示词

可以把一次模型调用想成一个纯函数：给它当前输入，它生成输出。大多数 API 调用不会自动记住你上一次发过什么；应用若需要多轮状态，就必须自行把相关消息和结果再次组织进请求。

因此，第二章是在回答第一章里“上下文”这个组成部分如何落地：**每次决策之前，系统怎样把任务所需的信息送到模型面前？**

书中按 API 视角讨论四种消息角色：`system`、`user`、`assistant` 和 `tool`。此外还会提供工具定义。角色帮助表达信息来自谁、处于对话流程的哪个位置；它们不是权限系统的替代品，不能因为文字标成 `system` 就把安全边界交给模型自行保证。

### 2.2 上下文是“本轮工作台”，不是全部数据仓库

典型上下文包括：系统规则、工具说明、用户目标、必要的历史消息、工具调用及其结果，以及本轮检索到的资料。它类似一次请求执行时准备好的局部工作区：模型只基于被放进来的材料工作。

这能解释一个常见现象：模型可能“知道”一般知识，却不知道你自己的数据库字段、仓库约定、刚发生的工具错误或内部流程。那些信息若没有通过上下文或工具交给它，它就不能稳定地据此行动。

上下文设计不是“越长越好”。它像给一个工程师准备工作台：少了关键图纸会做错，多到所有项目文件都摊在桌上也会找不着重点。目标是让与当前决策有关的信息可见、来源清楚、长度可控。

### 2.3 工具调用的消息往返

从 API 看，Agent 循环通常不是模型直接访问数据库，而是模型发出结构化工具请求，宿主程序执行，再把工具结果交回模型。也就是说：

```text
用户任务 → 模型请求 →（工具调用）→ 应用执行 → 工具结果 → 模型继续 → 最终答复
```

这里最重要的分工是：**模型提出行动，应用执行行动，应用还要验证行动是否被允许且成功。** 对开发者而言，这近似于模型产生一个待处理的命令对象，服务端按权限校验后执行，再把执行结果作为下一轮输入。工具调用不是“模型在回答里提到要查数据库”，而是协议层中的结构化交互。

### 2.4 稳定前缀、Chat Template 与缓存

书中讨论 KV Cache 和 Prompt Cache，是为了说明上下文的组织方式也会影响推理效率。直观地说，模型处理一段输入时会为已处理部分保留中间计算结果；如果连续请求共享相同前缀，某些服务可以复用这部分工作。若每次都改动前面的大段内容，复用机会会降低。

因此，常见组织思路是让相对稳定的系统规则和工具定义靠前，动态的用户输入、检索材料和工具结果靠后。不过实际缓存机制由模型服务和接口实现决定，缓存命中条件、收益和计费方式不能只靠这一条布局规则推断。

API 消息还会被转换成模型所需的 token 序列，这一转换有相应的 **Chat Template**。工程上的结论是使用服务/API 约定的消息格式，不要为了“更像模型输入”而自行拼接特殊 token；格式处理交给可靠的 SDK 或模型模板。

### 2.5 提示词、工具描述与 Skills：分别告诉模型怎么做、能做什么、去哪找方法

这几个概念常被混在一起，可以按职责区分：

| 组件    | 主要作用                   | 例子                    |
| ----- | ---------------------- | --------------------- |
| 系统提示词 | 规定目标、约束、风格或执行策略        | “遇到金额变更必须先核对账单”       |
| 工具定义  | 描述可执行能力、参数和结果          | `get_order(order_id)` |
| Skill | 提供某类任务的可复用流程或知识，通常按需加载 | “如何排查一次线上 500 错误”     |
| 当前状态  | 告知这次任务已完成什么、还有什么没做     | “已读取日志，尚未检查数据库”       |

可以把 Skill 看作一本按需翻阅的操作手册；工具则是手册里可能指向的实际按钮或接口。手册能指导如何做，但不等于执行能力本身。渐进式披露的价值是先让模型知道“有哪些能力/资料可用”，再在需要时装入细节，减少上下文负担。

提示注入提醒我们：用户文本、网页、文档和检索结果可能含有看起来像命令的内容。程序应尽量区分可信规则与待处理数据，并在工具执行端做权限校验；只在提示词里说“不要被恶意内容影响”不足以构成安全防护。

### 2.6 状态信息与上下文压缩：保留轨迹里的关键事实

长任务会积累大量工具输出和对话历史。状态信息可用很短的摘要记录任务目标、进度、决定和待办，让模型重新进入任务时更容易定位。它是上下文的索引/路标，不是完整历史的替代品。

压缩也不是单纯缩短文本。可用“交接班”来理解：下一位工程师不需要逐字读完整聊天，但必须知道目标、已做事项、证据、失败尝试、约束和下一步。压缩若删掉否定条件、错误信息或来源，可能让后续决策比原来更差。

另一个思路是**隔离而非压缩**：把独立子任务交给单独执行上下文，只将结论和必要证据带回主任务。这样类似把一项复杂工作交给另一个服务处理，避免把全部内部日志塞入主调用；前提是子任务描述清楚且结果可核验。
